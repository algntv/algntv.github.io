context / задача

хакатон Московского транспорта · команда 5 человек · 3 дня. работающий прототип системы прогнозирования задержек автобусов на остановках на 10–15 минут вперёд.

data / данные

потоковая телеметрия автобусов; текущие и прогнозные задержки на остановках.

process / работа

  • платформа принимает потоковую телеметрию и показывает текущие и прогнозные задержки в интерфейсе диспетчера;
  • реализованы live- и historical-режимы, ML-пайплайн, FastAPI backend и отдельный analytics worker;
  • решение контейнеризировано через Docker Compose и покрыто автоматическими тестами;
  • мой вклад: финальное code review, проверка прохождения тестов и end-to-end работоспособности проекта перед сдачей.

findings / результат

Результат команды — работающий прототип с live- и historical-режимами и горизонтом 10–15 минут. По документации ML-модуля, MAE финального ансамбля на holdout train→test составляет 40,6 с в режиме hint и 44,3 с в режиме stream без подсказки текущей задержки.

Это результаты офлайн-оценки команды из репозитория, а не измеренная точность в эксплуатации. Мой вклад — code review и проверка работоспособности перед сдачей; разработка модели относится к работе команды.

SQL / работа с данными

В командном backend используется оконная функция ROW_NUMBER: она выбирает последний прогноз для каждого автобуса. Сортировка по времени и ID даёт однозначный выбор при совпадении timestamps.

посмотреть SQL-пример
SELECT tr_id, t_forecast, predicted_delay_s
FROM (
    SELECT tr_id, t_forecast, predicted_delay_s,
           ROW_NUMBER() OVER (
               PARTITION BY tr_id
               ORDER BY t_forecast DESC, id DESC
           ) AS row_number
    FROM predictions
) AS ranked
WHERE row_number = 1
ORDER BY tr_id;

Упрощённый пример по коду команды. В historical-режиме исходный запрос дополнительно ограничивает прогнозы временем replay. Источник — backend команды; моя роль в проекте — code review и проверка работоспособности.
