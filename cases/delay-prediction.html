прогноз задержек транспорта

Командный хакатон Московского транспорта: показывать текущие задержки автобусов и прогнозировать их заранее в интерфейсе диспетчера.

формат

инструменты
Python / Docker / FastAPI / PyTorch

Задача

Дать диспетчеру представление не только о текущих задержках, но и о том, какие задержки ожидаются в ближайшее время. Для этого нужно связать поступающие данные автобусов, прогноз и отображение в одном работающем процессе.

Решение

Команда собрала прототип: платформа принимает телеметрию автобусов, формирует прогнозы задержек и показывает их в интерфейсе диспетчера.

В текущем режиме система работает с поступающими данными. В историческом режиме можно воспроизводить прошлые события и проверять работу решения.

Компоненты запускаются через Docker Compose. Автоматические тесты и проверка всего пути от данных до интерфейса помогают обнаружить ошибки на стыках системы.

Мой вклад

Провёл финальное code review, проверил прохождение тестов и сквозную работоспособность перед сдачей. Разработка модели и остальных компонентов относится к работе команды.

Выводы

  • Результат — работающий процесс, а не только модель. Прототип объединяет данные, прогнозирование и интерфейс; прогноз должен доходить до пользователя системы.
  • Текущий и исторический режимы решают разные задачи. Первый показывает происходящее сейчас, второй позволяет воспроизвести события и проверить поведение платформы.
  • Качество нужно проверять на двух уровнях. Офлайн-метрики описывают ошибку модели на тестовых данных. Сквозная проверка показывает, работает ли вся система вместе. Одна проверка не заменяет другую.

Прототип прогнозирует задержки на ближайшие 10–15 минут. Модель оценена на отложенных данных; это не подтверждение точности в реальной эксплуатации. Мой вклад был сосредоточен на проверке решения перед сдачей.

Результаты анализа

Результат команды — работающий прототип с live- и historical-режимами и горизонтом 10–15 минут. По документации ML-модуля, MAE финального ансамбля на holdout train→test составляет 40,6 с в режиме hint и 44,3 с в режиме stream без подсказки текущей задержки.

Это результаты офлайн-оценки команды из репозитория, а не измеренная точность в эксплуатации. Мой вклад — code review и проверка работоспособности перед сдачей; разработка модели относится к работе команды.

Выбор актуального прогноза

В командном backend используется оконная функция ROW_NUMBER: она выбирает последний прогноз для каждого автобуса. Сортировка по времени и ID даёт однозначный выбор при совпадении timestamps.

посмотреть SQL-пример
SELECT tr_id, t_forecast, predicted_delay_s
FROM (
    SELECT tr_id, t_forecast, predicted_delay_s,
           ROW_NUMBER() OVER (
               PARTITION BY tr_id
               ORDER BY t_forecast DESC, id DESC
           ) AS row_number
    FROM predictions
) AS ranked
WHERE row_number = 1
ORDER BY tr_id;

Упрощённый пример по коду команды. В historical-режиме исходный запрос дополнительно ограничивает прогнозы временем replay. Источник — backend команды; моя роль в проекте — code review и проверка работоспособности.
